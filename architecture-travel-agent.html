Travel Planner: structured generation and streaming chat

A trip planner that turns a short form into a full plan: an itinerary, attractions, dining, hidden gems and etiquette, plus a concierge chat that knows your preferences. Each request makes a single model call, and my code controls the flow. The model writes content into a fixed JSON schema, and the parts that should be predictable are computed in code.

Key decisions

The model writes content, code controls the flow

No agent loop. Every request does one known thing, and the page decides what happens next.

WhyPredictable latency and cost, and far fewer ways for a request to fail.

Schema-first generation

The prompt includes the exact JSON schema the plan must follow, the call runs in JSON mode, and the Worker strips code fences before parsing.

ResultThe UI renders straight from the parsed plan. Malformed output becomes a clear "try again" error instead of a broken page.

Predictable parts are computed, not generated

The budget breakdown, packing list and countdown timeline come from simple rules in the browser.

ResultFewer tokens per plan, and the numbers come out the same every time.

One stream format for two providers

Gemini and Groq stream in different formats. The Worker converts both to one {"delta"} frame format and drops Gemini's hidden reasoning text.

ResultThe chat UI works the same whichever provider the visitor picks.

Three request types, one endpoint

Browser Cloudflare (Worker, KV) Model provider

Generating a plan

  1. The visitor fills in city, country, duration, climate, budget tier, pace and activities, and picks a model.
  2. travel.js loads saved preferences and sends a generate request with the form values plus interests and dietary restrictions.
  3. The Worker clamps every field: duration 1 to 30 days, pace and budget tier from fixed lists, at most 10 activities of 60 characters each.
  4. It writes one prompt containing the trip details and the exact JSON schema to return. The itinerary is capped at 7 days even for longer trips.
  5. It makes a single non-streamed call with JSON mode on and up to 4,096 reply tokens, plus 1,024 of headroom for hidden reasoning.
  6. It strips any Markdown code fences, parses the JSON, and returns it. Malformed JSON becomes a 502 asking the visitor to try again.
  7. The page saves the trip with add_trip, then attaches the AI content and the locally computed sections with update_trip.
  8. The results tabs render from the saved trip, so a reload shows the same plan.

The budget, packing and timeline sections are always computed in the browser. Despite the "fallback" names, the model is never asked for them.

Concierge chat

  1. The page sends the question, the last 8 chat messages, the chosen model, and three saved preferences: interests, dietary restrictions and pace.
  2. The Worker cuts the question to 600 characters and keeps only user and assistant turns, 800 characters each.
  3. It builds a short system prompt that names the traveler's preferences.
  4. It calls the provider with streaming on and a 700-token reply cap.
  5. Each provider's stream is converted to the shared {"delta"} frames and relayed as it arrives.

The concierge has no access to saved trips, the current plan or any tools. Its only personal context is the three preference fields, so it cannot answer questions like "what is on day 2 of my Lisbon trip?".

The stream conversion handles one provider difference directly: Gemini separates events with CRLF and Groq with LF. It also drops Gemini's "thought" parts so reasoning text never reaches the chat.

Limitations and next steps

  • Grounding. Attractions, restaurants and prices come from the model's own knowledge, so they can be out of date. The next step is a places-lookup tool that verifies recommendations, the way the Chicago agent's tools do.
  • Concierge memory. The concierge sees only three preference fields, not saved trips. Adding the current plan to its context would let it answer questions like "what's on day 2 of my Lisbon trip?".
  • Per-visitor storage. In this demo, KV holds one shared preferences record and one shared trips record. Real users would need per-visitor keys and sign-in.
  • Shared code without a build step. Provider routing is copied from the Chicago Worker so each Worker deploys as one file. If more Workers are added, a small shared module would be worth a build step.
