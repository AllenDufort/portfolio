Chicago assistant: a tool-calling agent

An LLM agent that answers questions like "any Caribbean food near me?" using a personal map of about 550 saved places. The model never sees the place list. It gets the map's vocabulary and three search tools that I wrote, and a serverless back end runs those tools in a loop until the model can answer from real data.

Key decisions

Retrieve with tools, don't stuff the prompt

The smallest allowlisted models (the Groq ones) have an 8,000-token context, so all 550 rows can't go in the prompt. The model searches the data through three tools instead.

ResultFixed overhead is about 2,900 tokens, which leaves room for a question that takes three tool rounds.

Give the model the data's vocabulary

Early on, the model searched with its own wording and reported that a map with 40 Latin American places had none. The prompt now lists the sheet's actual types and sub-categories, and region words expand to countries and dishes.

ResultSearches use terms that actually exist in the data.

Meaning as well as keywords

Keywords only find what the sheet literally says, so "somewhere cozy for a rainy day" missed places noted as "candlelit" or "low-lit". search_places now takes a vibe: places are embedded from their name, type, sub-category and notes, and ranked by similarity to the question, alongside the keyword match.

ResultVague asks return fitting places. Vectors are built offline and committed, so a question costs one embedding call, and everything falls back to keywords if embeddings are unavailable.

Measure changes with an evaluation set

Prompt and tool edits used to be judged by trying a few questions. eval/cases.json holds 21 questions with the tools each should trigger and the places the answer should name, and eval/run.mjs scores every allowlisted model on tool choice and answer accuracy.

ResultA prompt change can be re-run against a saved baseline and shows which cases it fixed or broke, per model.

Answers stay grounded

Tools return match counts ("8 of 41"), report missing fields as "not listed", and compute distances themselves, so the model never estimates one.

ResultLess room for made-up facts, ratings or distances.

Streaming UX with honest errors

The tool loop runs before any output is sent, and the final text is then streamed in chunks. During provider rate-limit waits, a notice frame tells the visitor what's happening.

ResultErrors keep real HTTP status codes, and the chat still streams like a normal chat.

Request path and tool loop

Browser Inside the chicago-chat Worker External data

The model call goes to Claude (ids starting claude-) or Groq (everything else). The transcript is kept in a provider-neutral shape and converted to each API's format only when a request is built.

One question, step by step

  1. The widget sends {question, history, coords?, model?}. Coordinates are requested from the browser only when the question matches a "near me" pattern, and are rounded to 4 decimals.
  2. The Worker rejects foreign origins (403), throttles to 12 requests a minute per IP (429), and cuts the question to 500 characters.
  3. It resolves the model against the allowlist. Anything else silently becomes the default model.
  4. It loads the catalog: the sheet's rows, or the GeoJSON snapshot if the sheet fails. A warm Worker reuses the copy it built in the last 5 minutes.
  5. It writes the system prompt and appends the last 4 history messages (280 characters each, user and assistant roles only) plus the question.
  6. It calls the model without streaming, because a tool call can only be read from a complete JSON body.
  7. If the reply contains tool calls, the Worker runs each one against the catalog, appends the calls and results to the transcript, and calls the model again.
  8. If the reply has no tool calls, that text is the answer. After 5 tool rounds the next reply is taken as the answer regardless.
  9. The finished text is split on whitespace into chunks of about 90 characters and sent as {"delta"} frames, ending with [DONE].

Tools

ToolArgumentsBehavior
search_placesquery, vibe, type, neighborhood, limitComma-separated terms are OR-matched across name, type, sub-category and notes. Returns one line per place plus the total match count, so the model can say "8 of 41". Region words such as "caribbean" expand to every country, demonym and dish under them. vibe takes a mood or occasion in plain words and ranks places by embedding similarity; keyword hits get a small boost, and the result is labelled a ranking rather than a complete list.
get_place_detailsname, fields[]Matches the name in tiers (exact, prefix, substring, all words present) and returns only the best tier. Several matches come back as candidates for the model to ask about. A missing field is reported as "not listed" so the model does not invent one.
find_nearbytype, radius_miles, limitSorts saved places by haversine distance from the visitor, nearest first. Beyond 25 miles it reports that the visitor is out of town. Unavailable until the visitor shares a location.

Every tool returns plain text, caps limit at 12, and resolves everyday type words ("bookstore", "coffee shops") to the sheet's own Type labels.

Failure handling

  • Normal case keeps real status codes. The Worker holds its response until the loop finishes, so a failure can still be returned as a 4xx or 5xx with a sentence the visitor can act on.
  • Rate-limit waits open the stream early. If a provider returns 429, the Worker starts the response and sends a {"notice"} frame saying it is waiting. A later failure then arrives as an {"error"} frame, since the status code is already spent.
  • Searching without answering. If every round was spent on tools and no text came back, the visitor is told to try a simpler question.
  • Semantic search degrades to keywords. With no embeddings key, a missing embeddings.json or an embedding error, the vibe argument is ignored and the keyword search runs, so it can only add matches.
  • No canned fallback. There is no local retrieval. If the model cannot be reached, the widget says so.
  • Prompt injection through history. Only user and assistant turns are forwarded, so an injected system turn is dropped.
  • Not a general relay. The page cannot supply a prompt, only a question, so a leaked endpoint can only answer questions about this map.

What I'd build next

  • A judge for open questions. The evaluation set checks names in the answer against a hand-written pool. A model-graded pass could score whether a "cozy" answer actually reads as cozy.
  • Embeddings on a schedule. embed.mjs is run by hand after sheet edits. A scheduled job could rebuild and commit it, and a CI run of the evaluation set could gate prompt changes.
  • Usage analytics. Anonymous logs of which tools get called and which questions return nothing, to show where the vocabulary or the data has gaps.
