How this portfolio is built

Two of the projects on this site are full-stack AI apps. One is a tool-calling agent that answers questions about a live dataset of about 550 Chicago places. The other is an LLM trip planner with a streaming concierge chat. Both run on serverless back ends I wrote, with no framework, no build step and no API keys in the browser.

At a glance

Two LLM providers, one interface

Claude and Groq-hosted models sit behind one provider-neutral message format. Visitors pick a model and the back end routes by model id.

WhyFree-tier quotas run out. Being able to switch providers keeps the demos running.

Live data, no rebuild

A Google Sheet is the source of truth. Rows are parsed by header name, geocoded with Apps Script and Python, and backed by a GeoJSON snapshot.

ResultA place added to the sheet shows up on the map and in the agent's answers on the next load.

Keys never reach the browser

Model keys live as Worker secrets behind an origin allowlist, per-IP rate limits and server-written prompts.

ResultPublic demos with no exposed credentials, and the endpoints can't be used as a general-purpose LLM relay.

Zero dependencies

Native ES modules in the browser, single-file Workers, and test suites that run on Node's built-in runner.

ResultNothing to install or bundle. A clone runs with one command.

Not drawn: if the sheet is unreachable, both the map page and the chicago-chat Worker fall back to chicago_layers.geojson on GitHub Pages. The Worker also reads geocode_cache.json from there for rows that have no coordinates in the sheet, and embeddings.json (place vectors for the semantic vibe search, built offline by embed.mjs). The question itself is embedded at request time with Google's gemini-embedding-001, the one remaining Google dependency, used only for that search.

Data flow

Chicago map loads

  1. chicagoMap.js calls load() in chicagoData.js.
  2. It fetches the sheet as CSV and sheet.js parses rows by header name.
  3. Each row takes coordinates from the sheet's Lat/Lon, or else from geocode_cache.json. Rows with neither get no marker.
  4. If the sheet fails, the committed GeoJSON snapshot is used instead.
  5. Leaflet draws clustered markers and a filter chip per place type.

Visitor asks the Chicago assistant

  1. chicagoChat.js POSTs the question, recent history and chosen model. For "near me" questions it adds rounded coordinates.
  2. The Worker checks origin and rate limit (12 requests a minute per IP), then trims history to 4 turns.
  3. It builds the system prompt from the sheet's vocabulary of types and sub-categories. No place rows go in the prompt.
  4. The model calls search_places, get_place_details or find_nearby. The Worker runs them against its cached catalog for up to 5 rounds.
  5. The final text is re-framed as server-sent events and painted into the chat as it arrives.

Visitor plans a trip

  1. travel.js collects the form and calls travel-api.js, which POSTs one of three request types to the Worker.
  2. generate asks the model for a full plan as JSON (itinerary capped at 7 days). The Worker returns it in one response.
  3. The page saves the trip with db requests such as add_trip and update_trip, which read and write KV.
  4. concierge streams a chat reply back as server-sent events.
  5. travel-export.js opens a print window so a results tab can be saved as PDF.

Two LLM patterns side by side

I built the two apps differently on purpose. The Chicago assistant has to answer from private data, so it needs an agent with tools. Travel Planner needs creative content in a fixed shape, so one structured call is the simpler and cheaper choice. Details are in the Chicago agent and Travel Planner deep dives.

Security and cost controls

  • Keys stay server-side. ANTHROPIC_API_KEY and GROQ_API_KEY (plus GEMINI_API_KEY for embeddings) are Worker secrets pushed by each deploy.sh from the git-ignored .env. Nothing in the repo or a response contains them.
  • Origin allowlist. POSTs are accepted only from the GitHub Pages origin and a few localhost ports. Other origins get a 403.
  • Per-IP rate limits held in Worker memory, answered with 429 and Retry-After.
  • Model allowlist. Both Workers check the requested model against the shared list in assets/shared/models.js. Any other id falls back to the default, so a caller can't spend the keys on models the site doesn't offer.
  • Fixed prompt shape (Chicago). The Worker writes the prompt itself, drops any injected system turn, and pins temperature and token caps.
  • Health check. GET / on either Worker returns status JSON, including which provider keys are configured.

Engineering choices

  • No build step, on purpose. The site is hand-written HTML plus native ES modules, so what's in the repo is exactly what runs. The cost is no type checking or minification, which is acceptable at this size.
  • Two AI patterns, chosen per problem. The Chicago assistant needs facts from private data, so it uses a tool-calling agent. The Travel Planner needs creative content in a fixed shape, so it uses a single structured-output call. See the side-by-side comparison.
  • Single-file Workers. Each back end deploys as one worker.js with no dependencies. Provider-routing code is duplicated between them instead of shared through a package, which keeps deploys simple.
  • Graceful degradation. If the Google Sheet is unreachable, a committed GeoJSON snapshot keeps both the map and the agent working.

Limitations and next steps

  • Per-visitor storage. Travel Planner's KV holds one shared preferences record and one shared trips record, which is fine for a demo. Real users would need per-visitor keys and authentication.
  • Evaluation. A fixed set of test questions with expected answers would let me compare tool choice and accuracy across the allowlisted models and catch regressions when prompts change.
  • Grounding the trip planner. Plans come from the model's own knowledge. Adding a places lookup tool, the way the Chicago agent works, would make recommendations verifiable.
