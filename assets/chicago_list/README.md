# chicago_list

Data and front end for the Chicago map on the portfolio site. **A Google Sheet is the source of
truth** — the map page reads it on every page load, so editing the sheet updates the site with no
commit, no build, and no pipeline run.

[Chicago TODO sheet](https://docs.google.com/spreadsheets/d/18rG-azfyKrziKuDm3WBHD2UyMeeD5T8BMugFG7j5fw4/edit?gid=337826956#gid=337826956)
· columns: `Place`, `Type`, `Neighborhood`, `Reviews`, `Address`, `Lat`, `Lon`

## Files

### Runtime

| File | Description |
|------|-------------|
| `chicagoData.js` | **Builds the place data from the sheet on every page load** and hands it to the two consumers below through one memoised `ChicagoData.load()`, so the sheet is fetched once per visit. Must be loaded before them. See [Data flow](#data-flow). |
| `chicago_layers.geojson` | Committed snapshot, used only as the fallback when the sheet is unreachable or unshared. Regenerated by `geocode.py`. |

### Sheet tooling

| File | Description |
|------|-------------|
| `geocodeSheet.gs` | Apps Script that fills the sheet's `Lat`/`Lon` columns via `Maps.newGeocoder()` — free, no API key. Paste into Extensions → Apps Script, then use the **Chicago Map → Geocode missing rows** menu it adds. Installation notes are in the file header. |
| `geocode.py` | Refreshes the committed snapshot from the sheet, and geocodes any row whose `Lat`/`Lon` is still empty via Nominatim (cached). `--no-api` skips the geocoder. |
| `geocode_cache.json` | Persistent cache mapping street addresses → `[lon, lat]`, covering rows that have no `Lat`/`Lon` in the sheet yet. |

### Front-end

| File | Description |
|------|-------------|
| `chicagoMap.js` | Initialises the Leaflet map, registers custom zoom/locate/search controls, builds marker clusters from `ChicagoData.load()`, and wires up the layer toggles plus the Type filter row. Loaded by `chicagoMap.html` after the Leaflet and MarkerCluster CDN scripts. |
| `chicagoChat.js` | AI chat widget powered by the [Pollinations](https://pollinations.ai) text API — free, no API key, no visitor sign-in. On load it takes `ChicagoData.load()` and merges the overlapping layers into one place index. Each question is ranked against that index and only the top matches are sent as context, so the request stays small. When the API is throttled or slow, a local classical-NLP layer answers instead. See [Chat assistant](#chat-assistant) and [Local NLP fallback](#local-nlp-fallback). |

## Chat assistant

`chicagoChat.js` talks to Pollinations' OpenAI-compatible endpoint. It was chosen because it is the
only provider that works from a purely static page with **no API key committed to the repo and no
sign-in prompt for visitors** — it sends `Access-Control-Allow-Origin: *`, so the browser can call it
directly. (The previous puter.js integration required each visitor to have a Puter account.)

```
POST https://text.pollinations.ai/openai
{ "model": "openai-fast", "referrer": "...", "messages": [...] }
```

The free anonymous tier is the constraint the widget is designed around:

| Limit | Handling |
|-------|----------|
| ~1 request per 15s per visitor IP (`402` / `429` when exceeded) | Requests are paced from the last one; if the remaining wait exceeds `MAX_WAIT_MS` the question is answered locally instead of stalling. A `402`/`429` starts a 60s cooldown during which the API is skipped entirely. |
| A small per-IP spend budget, on top of the rate limit — once spent, every request returns `402` with `"API key budget too low. This request costs ~0.0003 pollen"` until it replenishes | Cost scales with prompt size, so only `CONTEXT_PLACES` (10) places are sent per question and notes are truncated to `NOTE_CHARS`. A visitor arrives with their own budget; when it runs out the widget answers locally. |
| Overlapping requests are refused (`queue full`) | Only one request is ever in flight; the input is disabled while a reply is pending. |
| `stream: true` is not available anonymously | Replies are fetched in one shot, then revealed with a typewriter effect so the UX still feels live. |
| `openai-fast` is the only anonymous model (`GET /models`) | Pinned in `API_MODEL`. It is a reasoning model, so the `reasoning` field in the response is ignored and only `content` is used. |

Because none of that is guaranteed, **the widget never depends on the network to answer.** Every
question is also resolved locally against the place index, and that answer is shown — tagged with a
short note — whenever the API is throttled, slow, or returns nothing.

## Local NLP fallback

The offline path is a small classical NLP stack rather than a keyword scan, so a throttled visitor
still gets a real answer. It has no dependencies, makes no network calls, and is built from the sheet
data at load — the whole index (552 merged places, ~1,750 term vocabulary) takes under 10 ms.

| Stage | What it does |
|-------|--------------|
| **Tokenizer + light Porter stemmer** | Steps 1a–1c only, which is where the wins are in this corpus: `pizzas`/`pizza`, `activities`/`activity`, `dining`/`dine`. Porter's later steps (`relational` → `relat`) blur distinct place names, so they are left out. Two tokenizers exist on purpose — retrieval drops function words, the intent classifier keeps them, because "how many" and "tell me about" are exactly the signal it learns from. |
| **BM25 ranking** | Replaced the hand-tuned `+4 / +2 / +1` field scoring. IDF makes terms that appear in hundreds of entries (`chicago`, `bar`, `street`) worth almost nothing on their own, which retired most of the old stop-word list — including the entries that only existed because prefix matching made `eat` collide with "Eately" and `town` with "Chinatown". Field weights (name 3×, notes/type/neighborhood 2×, address/layer 1×) keep a name hit ahead of a note hit. |
| **Coordination factor** | BM25 alone is a pure OR, so for `museums in hyde park` a rare-term single match could outrank a place matching every word. Each score is scaled by the share of the question's own words the place matched (floor 0.35), which fixes the order without discarding partial matches. Synonym expansions are excluded from the count so they cannot dilute it. |
| **Query expansion** | A hand-written synonym table (`ramen` → noodles, japanese, udon) folded through the same stemmer as the documents. Expansions are dropped when the corpus never uses them, and when they appear in more than 8% of entries, so an expanded query can only ever match vocabulary that really exists and can't be dragged off by a vague term. They score at 0.45 so a literal hit always wins. |
| **Trigram fuzzy matching** | Dice coefficient over padded character trigrams, used only when the lexical pass finds nothing: `tell me about abba` → **Aba**, `pizzza` → the pizza places. Also powers "did you mean", which reports a real spelling from the data rather than the stem the index stores. |
| **Naive Bayes intent classifier** | Multinomial NB with Laplace smoothing over ~50 labelled utterances, covering `count` / `category` / `nearby` / `lookup` / `search` / `greeting`. High-precision regex rules run first; the classifier handles the phrasings nobody wrote a pattern for ("somewhere for dinner"), and abstains to plain search when the per-token margin between the top two classes is too small. |
| **Haversine proximity** | `what's near X` resolves X against the sheet's own `Neighborhood` column first — averaging the real coordinates of the places filed under "Wicker Park" beats a hand-entered centroid and covers whatever neighborhoods the sheet uses — then a table of ~50 landmark centroids, then any saved place, then a street name. Results sort by real distance, with the radius widening (0.5 → 1 → 2 mi) until at least three match. Streets get a filter instead of a radius, since Clark St runs the length of the city. |

Ranking is shared with the remote path: the same BM25 pass chooses the `CONTEXT_PLACES` entries sent
to Pollinations, so a better retriever improves both answers.

```
"where can i eat ramen"   -> 8 ramen shops (category word dropped; synonyms add the izakayas)
"vegan food"              -> Soul Veg City   (via the "vegatarian" note the data actually contains)
"museums in hyde park"    -> the 4 Hyde Park museums first, other museums below
"what's near Wicker Park" -> nearest first, distances in miles, anchored on the sheet's own rows
"whats near clark st"     -> the saved places with Clark St in the address
```

## Data flow

```
Google Sheet ──gviz CSV──> chicagoData.js ──┬──> chicagoMap.js   (markers, layer + type filters)
 (source of truth)          (per page load) └──> chicagoChat.js  (place index for the assistant)
                                   │
                                   └── sheet unreachable? ──> chicago_layers.geojson (snapshot)
```

`chicagoData.js` reads the sheet through Google's gviz CSV endpoint
(`/gviz/tq?tqx=out:csv&gid=…`), which needs no API key and echoes the requesting origin in
`Access-Control-Allow-Origin`, so a purely static page can call it. **The sheet must stay shared as
"anyone with the link can view"** — if that changes, the endpoint stops answering and the page
silently falls back to the committed snapshot.

Coordinates are resolved in this order, per row:

1. The sheet's `Lat`/`Lon` columns — filled by `geocodeSheet.gs`. Preferred: no lookup at all.
2. `geocode_cache.json`, keyed by address. Only fetched when at least one row still lacks coordinates.
3. Neither — the row keeps a `null` geometry: no map marker, but still searchable in the chat, and the
   map's status line reports how many are waiting.

### Layers

`Type` determines the layer. A type may belong to more than one — the old KML filed every club under
both Food Spots and Activities, which is right, since a nightclub is both somewhere to drink and
something to do.

| Layer | Types | Count |
|-------|-------|-------|
| Chicago Todo List | everything | 553 |
| Food Spots | Restaurant, Bar, Cafe, Brunch, Snack, Market, Club | 462 |
| Activities | Museum, Landmark, Books, Park, Retail, Activity, Beach, Club | 117 |

A `Type` not in the table still appears in `Chicago Todo List`, and is logged to the console rather
than guessed into a layer — so a typo in the sheet is visible instead of silent. The mapping lives in
`TYPE_LAYERS` in **both** `chicagoData.js` and `geocode.py`; keep the two in sync.

Because a place can sit in two layers, the front end merges entries by name + address, leaving 552
distinct places that each remember every layer they belong to. (552 rather than 553: `La Scarola`
appears twice in the sheet with the same address.)

A second row of chips under the layer toggles filters by `Type` within whichever layers are on.
"All types" clears the filter; unchecking any single type clears "All types".

## Output format

`chicago_layers.geojson` — the fallback snapshot — is a JSON object keyed by layer name, each value a
GeoJSON FeatureCollection:

```json
{
  "Food Spots": {
    "type": "FeatureCollection",
    "features": [
      {
        "type": "Feature",
        "geometry": { "type": "Point", "coordinates": [-87.6298, 41.8781] },
        "properties": {
          "name": "Aba",
          "address": "302 N Green St, Chicago, IL 60607",
          "reviews": "Mediterranean food",
          "type": "Restaurant",
          "neighborhood": "West Loop"
        }
      }
    ]
  }
}
```

`type` and `neighborhood` are present whenever the data came from the sheet; the popup and the chat
both degrade gracefully without them.

## Updating

**Editing text, types, or neighborhoods:** just edit the sheet. Nothing else to do — the change is
live on the next page load.

**Adding a place:** add the row, then give it coordinates so it gets a pin:

```
Sheet -> Chicago Map -> Geocode missing rows
```

Until that runs, a new row is searchable in the chat and counted in the status line, but has no
marker. Rows that already have `Lat`/`Lon` are never re-geocoded, so the menu item is cheap to re-run.

**Refreshing the offline fallback** (worth doing occasionally, so the snapshot does not drift far
from the sheet):

```sh
python3 assets/chicago_list/geocode.py          # snapshot + geocode anything still missing
python3 assets/chicago_list/geocode.py --no-api  # snapshot only, no Nominatim calls
```

`geocode.py` runs in four phases: **fetch** the sheet as CSV, **load** `geocode_cache.json`,
**geocode** any row that has neither sheet coordinates nor a cache hit via
[Nominatim](https://nominatim.openstreetmap.org) (rate-limited to 1 request/second per their usage
policy, flushed to disk every 25 requests), then **emit** `chicago_layers.geojson`.

Note the division of labour: `geocodeSheet.gs` uses Google's geocoder and is the normal path, since
it writes coordinates back into the sheet where the site reads them. `geocode.py` uses Nominatim and
exists for the snapshot — it is the fallback's fallback.
