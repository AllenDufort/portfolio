# chicago_list

Data and front end for the Chicago map on the portfolio site. **A Google Sheet is the source of
truth** — the page reads it on every load, so editing the sheet updates the site with no commit and no
build.

[Chicago TODO sheet](https://docs.google.com/spreadsheets/d/18rG-azfyKrziKuDm3WBHD2UyMeeD5T8BMugFG7j5fw4/edit?gid=2011978534#gid=2011978534)
· columns: `Place`, `Type`, `Neighborhood`, `Reviews`, `Address`, `Lat`, `Lon`

## Files

| File | Description |
|------|-------------|
| `chicagoData.js` | **Builds the place data from the sheet on every page load**, memoised behind one `ChicagoData.load()` so the sheet is fetched once per visit. Must load first. The chat does not use it — the Worker reads the sheet itself. See [Data flow](#data-flow). |
| `chicagoMap.js` | The Leaflet map: custom zoom/locate/search controls, marker clusters, layer toggles, and the `Type` filter chips. Loaded after the Leaflet and MarkerCluster CDN scripts. |
| `chicagoChat.js` | Chat widget. Collects the question, adds the visitor's coordinates for "near me", POSTs to the Worker, renders the streamed reply. Holds no place data, so the chat works even if the map's load fails. See [Chat assistant](#chat-assistant). |
| `chicago_layers.geojson` | Committed snapshot — the fallback when the sheet is unreachable or unshared. Regenerated by `geocode.py`. |
| `geocodeSheet.gs` | Apps Script that fills the sheet's `Lat`/`Lon` via `Maps.newGeocoder()` — free, no API key. Paste into Extensions → Apps Script; it adds a **Chicago Map → Geocode missing rows** menu. |
| `geocode.py` | Refreshes the snapshot and geocodes any row still missing coordinates via Nominatim (cached). `--no-api` skips the geocoder. |
| `geocode_cache.json` | Address → `[lon, lat]` cache for rows the sheet has not geocoded yet. Read by `chicagoData.js` and the Worker. |
| `worker/worker.js` | Cloudflare Worker: holds the API keys as secrets, builds the prompt from the sheet, runs the tool loop, streams the reply. Owns `ALLOWED_MODELS`. See [Chat assistant](#chat-assistant). |
| `worker/wrangler.toml` | Worker name, default model, allowed origins, snapshot URL. All public — the keys are not in it. |
| `worker/deploy.sh` | Pushes `GEMINI_API_KEY` and `GROQ_API_KEY` as Worker secrets, then deploys. See [Deploying the Worker](#deploying-the-worker). |
| `worker/.dev.vars.example` | Copy to `.dev.vars` (gitignored) and paste your keys in for local runs. |

## Chat assistant

Every answer comes from [Gemini or Gemma](https://ai.google.dev/gemini-api/docs) or
[Groq](https://console.groq.com/docs), whichever the visitor picks in the Model dropdown. There is no
local retrieval layer and no fallback answer: if the model cannot be reached the widget says so.

**A key shipped to a static page is a public key**, so the keys live only as Worker secrets and the
browser never talks to a provider directly:

```
browser ──POST {question, history, coords?, model?}──> Worker ──> Gemini or Groq ──SSE──> browser
                                                        │
                                                        └── Google Sheet + geocode_cache.json (prompt)
```

The provider follows from the model id — `gemini-` or `gemma-` to Google, everything else to Groq.
The two APIs' different shapes (Gemini's `functionDeclarations` and `functionCall.args`; Groq's
OpenAI-shaped `tools` and JSON-string `arguments`) are normalised inside the Worker, so the page's
request and SSE envelope never change. **The Worker builds the prompt itself**, so nothing in a request
body can turn it into a general LLM proxy — the main risk of a paid key behind a public URL.

| Concern | How the Worker handles it |
|---------|---------------------------|
| The keys | `GEMINI_API_KEY` and `GROQ_API_KEY`, pushed by `deploy.sh`. Never in `wrangler.toml`, the repo, or a response. |
| Who may call it | `ALLOWED_ORIGINS` in `wrangler.toml`. A foreign origin gets `403` with no CORS header. |
| Abuse | 12 requests/minute per IP (`429` + `Retry-After`). Temperature and the token cap are pinned server-side. |
| The provider's own rate limit | A Groq/Gemini `429` is retried once, waiting as long as its `Retry-After` asks (1–20s; 5s if it sends none), and the visitor is told so mid-wait. Total waiting per question is capped at 45s, under the client's 90s. Never applied to the Worker's own `429` above — that one is meant to slow a caller down. |
| Which model a caller may pick | `ALLOWED_MODELS` in `worker.js`. Anything else, including a hand-edited request, silently falls back to the default, so a leaked endpoint cannot be pointed at an expensive model. |
| Prompt injection through history | Only `user` and `assistant` turns are forwarded; an injected `system` turn is dropped. History is capped at 6 turns and 600 chars, the question at 500. |
| Sheet outages | Same fallback the map uses: the sheet, then `chicago_layers.geojson`. The catalog is cached 5 minutes, so a burst of questions is one sheet fetch. |
| A dead endpoint | `GET /` returns health JSON — place and neighborhood counts, data source, the counted `Type` vocabulary and sub-category count behind the prompt, prompt size, default model and allowlist, which keys are set. Never a key itself. |

### The prompt is the map's vocabulary, not the map

Place data reaches the model through three tools — `search_places`, `get_place_details`,
`find_nearby` — so the prompt carries no rows. It carries the two vocabularies `buildCatalog` counts
out of the sheet: every `Type` value, and every sub-category at the head of a `description` ("Mexican
restaurant", "Comic book store"). Neither is guessable from outside the sheet, which is the whole
reason they are in the prompt. A visitor asks for *bookstores* and the column says `Books`; a visitor
asks for *latino restaurants* and the sheet records only `Mexican restaurant`, `Cuban restaurant`,
`Peruvian restaurant` and the like, plus a `Taco restaurant` filed under `Bar`. Without the real words
the model searched for the visitor's, missed, and called a map holding 40 Latin American places empty.

So a theme costs one call, `search_places` **OR**s `query` as comma-separated terms across each
place's name, type, sub-category and notes, and resolves `type` against the counted vocabulary rather
than literally — *bookstores*, *coffee shops* and *things to do* reach `Books`, `Cafe` and `Activity`,
while a word outside it (*barbecue*, *speakeasy*) narrows as a keyword instead of emptying the result.
Counts ride along because they set expectations: `Colombian restaurant (1)` makes a single hit a
complete answer. Both are recounted per refresh, so a new `Type` reaches the prompt within the
5-minute cache window with no code change.

### Streaming

No upstream round is streamed: a tool call can only be parsed out of a whole JSON body, and the round
where the model stops calling tools is the round where it writes the reply. The Worker keeps that text
and re-frames it as the SSE the page already reads (`{"delta"}` frames, an optional `{"error"}`, then
`[DONE]`), chunked on whitespace so a long answer paints in reading order. Re-requesting the turn with
`stream: true` to get provider SSE instead costs a second full-prompt call and can return nothing at
all — a fresh sample of an already-answered turn sometimes calls a tool. Upstream status codes
(401/429/5xx) map to sentences a visitor can act on; the client warns at 9s and gives up at 90s.

The one thing that has to be said before the answer is a rate-limit wait. Groq answers a
token-budget `429` with `Retry-After: 12`, and twelve silent seconds are indistinguishable from
a hung widget — so the first wait opens the stream early and sends a `{"notice"}` frame, which
the page shows in the status line and never folds into the reply or the history. That trade is
why the channel stays shut otherwise: a buffered response can still carry a real status code,
and once a byte is out the status line is spent. Measured over a burst that rate-limited every
question, honouring `Retry-After` answered all five; a fixed 5s wait, spent before Groq was
ready, had failed two of them.

### "Near me"

The one thing a prompt cannot answer alone. `NEAR_ME_RE` in `chicagoChat.js` — the only hardcoded
language rule left — decides whether to ask the browser for coordinates. If they are shared the Worker
does the geometry and hands the model a finished, sorted list, so it never estimates a distance:

```
NEAR THE VISITOR (straight-line miles from where they are, which is in South Loop, nearest first, 14 shown):
- Low Country (Restaurant) | 0.1 mi | South Loop
- Yolk (Brunch) | 0.2 mi | South Loop
```

The radius widens (0.5 → 1 → 2 mi) until five places qualify. The visitor's neighborhood comes from
averaging the coordinates of the places filed under each one, so no hand-entered centroid table can
drift. Past 25 miles out the heading tells the model to say they are too far, rather than present a
700-mile drive as "nearby".

Privacy: coordinates are rounded to 4 decimals (~11 m) before they leave the browser, sent only on
questions about nearby places, held in memory for 5 minutes so follow-ups stay anchored, and never
stored — not in the Worker, not in `localStorage`.

### Running the map locally

Serve the repo over HTTP rather than opening the file directly — `file://` has no origin for the
sheet's CORS check, and geolocation needs a secure context, which `localhost` counts as:

```sh
cd <repo root>
python3 -m http.server 8000     # then open http://localhost:8000/chicagoMap.html
```

That covers the map, layers, filters, search, and locate. The chat needs the Worker alongside it:

```sh
cd assets/chicago_list/worker
cp .dev.vars.example .dev.vars          # gitignored; paste your API keys here
npx wrangler dev --config wrangler.toml # serves the Worker at http://127.0.0.1:8787
```

The `--config` flag is not optional: without it wrangler walks up, finds the repo-root
`wrangler.jsonc`, and dies trying to serve the repo's `.git` pack as static assets
(`Asset too large … 112 MiB`). Use `wrangler dev` here, not `deploy.sh` — that deploys to production.

`chicagoChat.js` switches to the dev URL itself on `localhost` or `127.0.0.1`, so nothing needs
editing. Port 8000 matters: it is in `ALLOWED_ORIGINS` along with 5500 (VS Code Live Server), and any
other port gets a `403` until added there. Skipping the Worker leaves the map fully working and the
chat saying it is not connected.

### Deploying the Worker

**Prerequisites:** a free [Cloudflare account](https://dash.cloudflare.com/sign-up), a
[Gemini](https://aistudio.google.com/apikey) and/or [Groq](https://console.groq.com/keys) API key, and
`WRANGLER_WORKER_NAME` plus at least one of `GEMINI_API_KEY` / `GROQ_API_KEY` in the repo-root `.env`
(see `.env.example`). With one key set, the other provider's models return a clear error.

Log in to Cloudflare once, then run from anywhere in the repo:

```sh
bash assets/chicago_list/worker/deploy.sh
```

It loads `.env`, pipes whichever keys are set in as Worker secrets — never touching shell history or
the repo — then `cd`s into `worker/` and deploys, printing the live URL. It exits on any failure
(`set -euo pipefail`), including a missing `WRANGLER_WORKER_NAME` or no key at all. That `cd` is what
avoids the `Asset too large` failure above, which is also why not to run wrangler from the repo root.

After the first deploy, put the printed URL in `WORKER_URL` at the top of `chicagoChat.js` and commit
it along with `worker/` — nothing in there holds a key. Until it is set the widget says it is not
connected rather than failing with a network error. Then verify:

```sh
curl https://chicago-chat.chicagochat.workers.dev
```

Look for `"ok":true`, `"source":"sheet"`, and `true` for each provider under `"keyConfigured"`. A
`false` means that secret push did not land — re-run `deploy.sh`. `"source":"snapshot"` means the sheet
fetch failed and answers come from the committed GeoJSON. Re-running `deploy.sh` also rotates a key: it
pushes secrets before deploying, so the new one goes live atomically.

## Data flow

```
Google Sheet ──gviz CSV──> chicagoData.js ────> chicagoMap.js   (markers, layer + type filters)
 (source of truth)     │    (per page load) │
                       │                    └── sheet unreachable? ──> chicago_layers.geojson
                       │
                       └──gviz CSV──> worker/worker.js ──> Gemini or Groq ──> chicagoChat.js
                                       (prompt, 5-min cache)  (page's choice)  (streamed reply)
```

Two independent readers of the same sheet: the map in the browser, the Worker server-side. Both use
Google's gviz CSV endpoint (`/gviz/tq?tqx=out:csv&gid=…`), which needs no API key and echoes the
requesting origin in `Access-Control-Allow-Origin`, so a static page can call it. **The sheet must stay
shared as "anyone with the link can view"** — otherwise the endpoint stops answering and both readers
fall back to the snapshot.

Coordinates resolve in this order, per row, for both readers:

1. The sheet's `Lat`/`Lon` columns, filled by `geocodeSheet.gs`. Preferred: no lookup at all.
2. `geocode_cache.json`, keyed by address. Only fetched when a row still lacks coordinates.
3. Neither — the row keeps a `null` geometry: no marker, and no distance in a "near me" answer, though
   it is still searchable and the map's status line reports how many are waiting.

### Layers

`Type` determines the layer, and a type may belong to more than one — the old KML filed every club
under both Food Spots and Activities, which is right: a nightclub is both a place to drink and
something to do.

| Layer | Types | Count |
|-------|-------|-------|
| Chicago Todo List | everything | 553 |
| Food Spots | Restaurant, Bar, Cafe, Brunch, Snack, Market, Club | 462 |
| Activities | Museum, Landmark, Books, Park, Retail, Activity, Beach, Club | 117 |

A `Type` not in the table still appears in `Chicago Todo List` and is logged to the console rather
than guessed into a layer, so a sheet typo is visible instead of silent. The mapping lives in
`TYPE_LAYERS` in `chicagoData.js`, `geocode.py`, and `worker/worker.js` — keep the three in sync.

Because a place can sit in two layers, both readers merge by name + address, leaving 552 distinct
places that each remember every layer they belong to. (552 rather than 553: `La Scarola` appears twice
with the same address.) A second chip row filters by `Type` within whichever layers are on; "All types"
clears the filter, and unchecking any single type clears "All types".

## Output format

`chicago_layers.geojson` — the fallback snapshot — is an object keyed by layer name, each value a
GeoJSON `FeatureCollection` of `Point` features:

```json
{ "Food Spots": { "type": "FeatureCollection", "features": [
  { "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [-87.6298, 41.8781] },
    "properties": { "name": "Aba", "address": "302 N Green St, Chicago, IL 60607",
                    "reviews": "Mediterranean food", "type": "Restaurant",
                    "neighborhood": "West Loop" } }
] } }
```

`type` and `neighborhood` are present whenever the data came from the sheet; the popup and the chat
both degrade gracefully without them.

## Updating

**Editing text, types, or neighborhoods:** just edit the sheet — live on the next page load.

**Adding a place:** add the row, then give it coordinates so it gets a pin:

```
Sheet -> Chicago Map -> Geocode missing rows
```

Until that runs the row is searchable by the chat and counted in the status line, but has no marker
and no distance in a "near me" answer. Rows that already have `Lat`/`Lon` are never re-geocoded, so
the menu item is cheap to re-run. The chat picks the row up within 5 minutes, the map on next load.

**Refreshing the offline fallback** (worth doing occasionally, so the snapshot does not drift):

```sh
python3 assets/chicago_list/geocode.py           # snapshot + geocode anything still missing
python3 assets/chicago_list/geocode.py --no-api  # snapshot only, no Nominatim calls
```

`geocode.py` fetches the sheet as CSV, loads `geocode_cache.json`, geocodes any row with neither sheet
coordinates nor a cache hit via [Nominatim](https://nominatim.openstreetmap.org) (1 request/second per
their usage policy, flushed every 25), then emits `chicago_layers.geojson`.

Note the division of labour: `geocodeSheet.gs` uses Google's geocoder and is the normal path, since it
writes coordinates back into the sheet where the site reads them. `geocode.py` uses Nominatim and
exists only for the snapshot — the fallback's fallback.
