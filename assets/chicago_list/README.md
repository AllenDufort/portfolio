# chicago_list

Data and front end for the Chicago map on the portfolio site. **A Google Sheet is the source of
truth** — the map page reads it on every page load, so editing the sheet updates the site with no
commit, no build, and no pipeline run.

[Chicago TODO sheet](https://docs.google.com/spreadsheets/d/18rG-azfyKrziKuDm3WBHD2UyMeeD5T8BMugFG7j5fw4/edit?gid=2011978534#gid=2011978534)
· columns: `Place`, `Type`, `Neighborhood`, `Reviews`, `Address`, `Lat`, `Lon`

## Files

### Runtime

| File | Description |
|------|-------------|
| `chicagoData.js` | **Builds the place data from the sheet on every page load** and hands it to `chicagoMap.js` through one memoised `ChicagoData.load()`, so the sheet is fetched once per visit. Must be loaded first. The chat does not use it — the Worker reads the sheet itself. See [Data flow](#data-flow). |
| `chicago_layers.geojson` | Committed snapshot, used only as the fallback when the sheet is unreachable or unshared. Regenerated by `geocode.py`. |

### Sheet tooling

| File | Description |
|------|-------------|
| `geocodeSheet.gs` | Apps Script that fills the sheet's `Lat`/`Lon` columns via `Maps.newGeocoder()` — free, no API key. Paste into Extensions → Apps Script, then use the **Chicago Map → Geocode missing rows** menu it adds. Installation notes are in the file header. |
| `geocode.py` | Refreshes the committed snapshot from the sheet, and geocodes any row whose `Lat`/`Lon` is still empty via Nominatim (cached). `--no-api` skips the geocoder. |
| `geocode_cache.json` | Persistent cache mapping street addresses → `[lon, lat]`, covering rows that have no `Lat`/`Lon` in the sheet yet. Read by `chicagoData.js` and by the Worker. |

### Chat back end (`worker/`)

| File | Description |
|------|-------------|
| `worker/worker.js` | Cloudflare Worker. Holds the OpenRouter key as a server-side secret, builds the whole prompt from the sheet itself, and streams the model's reply back as SSE. See [Chat assistant](#chat-assistant). |
| `worker/wrangler.toml` | Deploy config: Worker name, model, allowed origins, snapshot URL. Everything here is public — the key is not in it. |
| `worker/.dev.vars.example` | Template for local runs. Copy to `.dev.vars` (gitignored) and paste your key in for `wrangler dev`. |

### Front-end

| File | Description |
|------|-------------|
| `chicagoMap.js` | Initialises the Leaflet map, registers custom zoom/locate/search controls, builds marker clusters from `ChicagoData.load()`, and wires up the layer toggles plus the Type filter row. Loaded by `chicagoMap.html` after the Leaflet and MarkerCluster CDN scripts. |
| `chicagoChat.js` | Chat widget. Every answer comes from an LLM — there is no retrieval, ranking, or fallback layer in the browser. It collects a question, adds the visitor's coordinates when they ask what is near them, POSTs to the Worker below, and renders the streamed reply. It needs no place data and does not call `ChicagoData.load()`. See [Chat assistant](#chat-assistant). |

## Chat assistant

Every answer comes from an LLM on [OpenRouter](https://openrouter.ai). There is no local retrieval
layer and no fallback answer: if the model cannot be reached, the widget says so rather than showing a
quiet substitute that would read like a bad reply.

The browser never talks to OpenRouter. **A key shipped to a static page is a public key**, so it lives
only as a Cloudflare Worker secret and the page talks to the Worker:

```
browser ──POST {question, history, coords?}──> Worker ──> OpenRouter ──SSE──> browser
                                                 │
                                                 └── Google Sheet + geocode_cache.json (prompt)
```

The Worker is not a plain relay. **It builds the prompt itself**, from the same sheet the map reads, so
the endpoint can only ever answer questions about this map — there is nothing in the request body that
lets a caller use it as a general LLM proxy.

| Concern | How the Worker handles it |
|---------|---------------------------|
| The key | `OPENROUTER_API_KEY`, set with `wrangler secret put`. Never in `wrangler.toml`, the repo, or a response. |
| Who may call it | `ALLOWED_ORIGINS` in `wrangler.toml`. A foreign origin gets `403` with no CORS header. |
| Abuse | 12 requests/minute per IP (`429` + `Retry-After`). The model, temperature, and token cap are pinned server-side. |
| Prompt injection through history | Only `user` and `assistant` turns are forwarded; an injected `system` turn is dropped. History is capped at 6 turns and 600 chars, the question at 500. |
| Sheet outages | Same fallback the map uses: the sheet, then `chicago_layers.geojson`. The built catalog is cached for 5 minutes, so a burst of questions is one sheet fetch. |
| A dead endpoint | `GET /` returns a health JSON — place count, neighborhood count, whether the data came from the sheet or the snapshot, prompt size, model, and whether the key is configured. It never reveals the key itself. |

**The prompt is the whole map.** All 552 places with their notes come to ~34 KB (~8.5k tokens) against
the model's 1M-token context, so nothing is pre-selected and no place can be hidden from a question
that asks for it. Places are grouped under `## Neighborhood (count)` headings, which is what makes
*"what food spots are in South Loop?"* reliable — the answer is one contiguous, counted block instead
of 552 rows to filter — and lets the model answer "how many" from a heading rather than by counting.

Replies stream. The Worker normalises OpenRouter's SSE into one shape (`{"delta"}`, `{"error"}`,
`[DONE]`), drops reasoning tokens, and maps upstream status codes (401/402/429/5xx) to sentences a
visitor can act on. Streaming is not cosmetic here: a 550B model on a free endpoint takes seconds to
start, and the client also shows a "still thinking" note at 9s and gives up at 90s.

### "Near me"

The one thing a prompt cannot answer alone. `NEAR_ME_RE` in `chicagoChat.js` — the only hardcoded
language rule left — decides whether to ask the browser for coordinates. If they are shared, the
Worker does the geometry and hands the model a finished, sorted list, so the model never estimates a
distance:

```
NEAR THE VISITOR (straight-line miles from where they are, which is in South Loop, nearest first, 14 shown):
- Low Country (Restaurant) | 0.1 mi | South Loop
- Yolk (Brunch) | 0.2 mi | South Loop
```

The radius widens (0.5 → 1 → 2 mi) until at least five places qualify. The visitor's own neighborhood
is derived by averaging the coordinates of the places filed under each one — the sheet's rows define
the areas, so there is no hand-entered centroid table to drift. A visitor further than 25 miles out
gets a heading that tells the model to say they are too far, rather than presenting a 700-mile drive as
"nearby".

Privacy: coordinates are rounded to 4 decimal places (~11 m) before they leave the browser, sent only
on questions that ask about nearby places, held in memory for 5 minutes so follow-ups stay anchored,
and never stored — not in the Worker, not in `localStorage`.

### Running the map locally

Serve the repo over HTTP rather than opening the file directly — `file://` has no origin for the
sheet's CORS check, and geolocation needs a secure context, which `localhost` counts as:

```sh
cd <repo root>
python3 -m http.server 8000     # then open http://localhost:8000/chicagoMap.html
```

That is enough for the map, layers, type filters, search, and the locate control. The chat needs the
Worker running alongside it, in a second terminal:

```sh
cd assets/chicago_list/worker
cp .dev.vars.example .dev.vars   # gitignored; paste the key here
npx wrangler dev                 # http://127.0.0.1:8787
```

`chicagoChat.js` switches to the dev URL by itself when the page's hostname is `localhost` or
`127.0.0.1`, so nothing needs editing to test. Port 8000 matters: it is in `ALLOWED_ORIGINS` along
with 5500 (VS Code Live Server), and any other port gets a `403` from the Worker until it is added
there. Skipping the Worker leaves the map fully working and the chat saying it is not connected.

### Deploying the Worker

**Run these from `assets/chicago_list/worker`, not the repo root.** With no config file in sight,
wrangler assumes the current directory is a static-assets Worker, scans everything including `.git`,
and fails on the pack file — `Asset too large … 112 MiB`. From the worker directory it reads
`wrangler.toml`, sees `main = "worker.js"`, and uploads one script with no asset scan.

```sh
cd assets/chicago_list/worker
npx wrangler login                                                      # free Cloudflare account is enough
set -a; source ../../../.env; set +a                                    # set up env
npx wrangler secret put OPENROUTER_API_KEY --name $WRANGLER_WORKER_NAME # paste the key; it never touches the repo
npx wrangler deploy --config wrangler.toml --name $WRANGLER_WORKER_NAME # prints https://chicago-chat.chicagochat.workers.dev
```

To stay at the repo root instead, pass `--config assets/chicago_list/worker/wrangler.toml` — paths
inside the config resolve relative to the config file, so `worker.js` still resolves.

Then put the printed URL in `WORKER_URL` at the top of `chicagoChat.js` and commit, along with
`worker/`. Nothing there holds the key, so all of it is safe to commit. Until `WORKER_URL` is set the
widget says it is not connected instead of failing with a network error.

Check it answered:

```sh
curl https://chicago-chat.chicagochat.workers.dev
```

Look for `"ok":true`, `"source":"sheet"`, and `"keyConfigured":true`. `keyConfigured: false` means the
`secret put` did not land; `"source":"snapshot"` means the sheet fetch failed and answers are coming
from the committed GeoJSON instead.

Changing the model later is an edit to `MODEL` in `wrangler.toml` plus another `deploy`. Rotating the
key is another `wrangler secret put` with no redeploy.

## Data flow

```
Google Sheet ──gviz CSV──> chicagoData.js ────> chicagoMap.js   (markers, layer + type filters)
 (source of truth)     │    (per page load) │
                       │                    └── sheet unreachable? ──> chicago_layers.geojson
                       │
                       └──gviz CSV──> worker/worker.js ────> OpenRouter ────> chicagoChat.js
                                       (prompt, 5-min cache)                  (streamed reply)
```

Two independent readers of the same sheet. The map reads it in the browser; the Worker reads it
server-side to build the prompt. `chicagoChat.js` reads no place data at all, which is why the chat
keeps working even if the map's own load fails.

`chicagoData.js` reads the sheet through Google's gviz CSV endpoint
(`/gviz/tq?tqx=out:csv&gid=…`), which needs no API key and echoes the requesting origin in
`Access-Control-Allow-Origin`, so a purely static page can call it. **The sheet must stay shared as
"anyone with the link can view"** — if that changes, the endpoint stops answering and the page
silently falls back to the committed snapshot.

Coordinates are resolved in this order, per row — by `chicagoData.js` and by the Worker alike:

1. The sheet's `Lat`/`Lon` columns — filled by `geocodeSheet.gs`. Preferred: no lookup at all.
2. `geocode_cache.json`, keyed by address. Only fetched when at least one row still lacks coordinates.
3. Neither — the row keeps a `null` geometry: no map marker, and no distance in a "near me" answer,
   though the place is still in the prompt and the map's status line reports how many are waiting.

### Layers

`Type` determines the layer. A type may belong to more than one — the old KML filed every club under
both Food Spots and Activities, which is right, since a nightclub is both somewhere to drink and
something to do.

| Layer | Types | Count |
|-------|-------|-------|
| Chicago Todo List | everything | 553 |
| Food Spots | Restaurant, Bar, Cafe, Brunch, Snack, Market, Club | 462 |
| Activities | Museum, Landmark, Books, Park, Retail, Activity, Beach, Club | 117 |

A `Type` not in the table still appears in `Chicago Todo List`, and is logged to the console rather
than guessed into a layer — so a typo in the sheet is visible instead of silent. The mapping lives in
`TYPE_LAYERS` in `chicagoData.js`, `geocode.py`, and `worker/worker.js`; keep the three in sync.

Because a place can sit in two layers, both readers merge entries by name + address, leaving 552
distinct places that each remember every layer they belong to. (552 rather than 553: `La Scarola`
appears twice in the sheet with the same address.)

A second row of chips under the layer toggles filters by `Type` within whichever layers are on.
"All types" clears the filter; unchecking any single type clears "All types".

## Output format

`chicago_layers.geojson` — the fallback snapshot — is a JSON object keyed by layer name, each value a
GeoJSON FeatureCollection:

```json
{
  "Food Spots": {
    "type": "FeatureCollection",
    "features": [
      {
        "type": "Feature",
        "geometry": { "type": "Point", "coordinates": [-87.6298, 41.8781] },
        "properties": {
          "name": "Aba",
          "address": "302 N Green St, Chicago, IL 60607",
          "reviews": "Mediterranean food",
          "type": "Restaurant",
          "neighborhood": "West Loop"
        }
      }
    ]
  }
}
```

`type` and `neighborhood` are present whenever the data came from the sheet; the popup and the chat
both degrade gracefully without them.

## Updating

**Editing text, types, or neighborhoods:** just edit the sheet. Nothing else to do — the change is
live on the next page load.

**Adding a place:** add the row, then give it coordinates so it gets a pin:

```
Sheet -> Chicago Map -> Geocode missing rows
```

Until that runs, a new row still reaches the chat's prompt and the status line counts it, but it has
no marker and no distance in a "near me" answer. Rows that already have `Lat`/`Lon` are never
re-geocoded, so the menu item is cheap to re-run. The chat picks the row up within 5 minutes (the
Worker's catalog cache); the map picks it up on the next page load.

**Refreshing the offline fallback** (worth doing occasionally, so the snapshot does not drift far
from the sheet):

```sh
python3 assets/chicago_list/geocode.py          # snapshot + geocode anything still missing
python3 assets/chicago_list/geocode.py --no-api  # snapshot only, no Nominatim calls
```

`geocode.py` runs in four phases: **fetch** the sheet as CSV, **load** `geocode_cache.json`,
**geocode** any row that has neither sheet coordinates nor a cache hit via
[Nominatim](https://nominatim.openstreetmap.org) (rate-limited to 1 request/second per their usage
policy, flushed to disk every 25 requests), then **emit** `chicago_layers.geojson`.

Note the division of labour: `geocodeSheet.gs` uses Google's geocoder and is the normal path, since
it writes coordinates back into the sheet where the site reads them. `geocode.py` uses Nominatim and
exists for the snapshot — it is the fallback's fallback.
