# chicago_list

Data and front end for the Chicago map on the portfolio site. **A Google Sheet is the source of truth** —
the page reads it on every load, so editing the sheet updates the site with no commit and no build.
[Chicago TODO sheet](https://docs.google.com/spreadsheets/d/18rG-azfyKrziKuDm3WBHD2UyMeeD5T8BMugFG7j5fw4/edit?gid=2011978534#gid=2011978534)
· columns: `Place`, `Type`, `Neighborhood`, `Reviews`, `Address`, `Lat`, `Lon`

## Files

| File | Description |
|------|-------------|
| `chicagoData.js` | Builds the place data from the sheet per page load, memoised behind one `ChicagoData.load()`. Must load first. The chat bypasses it — the Worker reads the sheet itself. |
| `chicagoMap.js` | Leaflet map: custom zoom/locate/search controls, marker clusters, `Type` filter chips. Loads after the Leaflet and MarkerCluster CDN scripts. |
| `chicagoChat.js` | Chat widget: question in, coordinates added for "near me", POST to the Worker, streamed reply out. Holds no place data, so it survives a failed map load. |
| `chicago_layers.geojson` | Committed snapshot — the fallback when the sheet is unreachable or unshared. Regenerated by `geocode.py`. |
| `geocodeSheet.gs` | Apps Script filling the sheet's `Lat`/`Lon` via `Maps.newGeocoder()` — free, no API key. Adds a **Chicago Map → Geocode missing rows** menu. |
| `geocode.py` | Refreshes the snapshot, geocoding rows still missing coordinates via Nominatim (cached). `--no-api` skips the geocoder. |
| `geocode_cache.json` | Address → `[lon, lat]` cache for rows the sheet has not geocoded yet. Read by `chicagoData.js` and the Worker. |
| `worker/worker.js` | The Worker: keys as secrets, prompt built from the sheet, tool loop, streamed reply. Owns `ALLOWED_MODELS`. |
| `worker/wrangler.toml` | Worker name, default model, allowed origins, snapshot URL. All public — no keys. |
| `worker/deploy.sh` | Pushes `GEMINI_API_KEY` and `GROQ_API_KEY` as Worker secrets, then deploys. |
| `worker/.dev.vars.example` | Copy to `.dev.vars` (gitignored) and paste your keys in for local runs. |

## Chat assistant

Answers come from [Gemini or Gemma](https://ai.google.dev/gemini-api/docs) or
[Groq](https://console.groq.com/docs), whichever the visitor picks — no local retrieval and no canned fallback,
so if the model cannot be reached the widget says so. **A key shipped to a static page is a public key**, so
keys live only as Worker secrets.

```
browser ──POST {question, history, coords?, model?}──> Worker ──> Gemini or Groq ──SSE──> browser
                                                        │
                                                        └── Google Sheet + geocode_cache.json (prompt)
```

Provider follows from the model id — `gemini-`/`gemma-` to Google, everything else to Groq — and both APIs'
shapes are normalised inside the Worker, so the page's request and SSE envelope never change. **The Worker
builds the prompt itself**, so no request body can turn it into a general LLM proxy.

| Concern | How the Worker handles it |
|---------|---------------------------|
| The keys | `GEMINI_API_KEY`, `GROQ_API_KEY`, pushed by `deploy.sh`. Never in `wrangler.toml`, the repo, or a response. |
| Who may call it | `ALLOWED_ORIGINS` in `wrangler.toml`. A foreign origin gets `403`, no CORS header. |
| Abuse | 12 requests/min per IP (`429` + `Retry-After`). Temperature and token cap pinned server-side. |
| The provider's rate limit | Retried once honouring its `Retry-After` (1–20s; 5s if absent), capped at 45s/question under the client's 90s. Never applied to the Worker's own `429` — that one slows a caller down. |
| Which model a caller may pick | `ALLOWED_MODELS` in `worker.js`. Anything else falls back to the default, so a leaked endpoint cannot reach an expensive model. |
| Injection through history | Only `user`/`assistant` turns forwarded; an injected `system` turn is dropped. History capped at 4 turns × 280 chars, the question at 500. |
| Sheet outages | Same fallback as the map: sheet, then `chicago_layers.geojson`. Catalog cached 5 min, so a burst of questions is one sheet fetch. |
| A dead endpoint | `GET /` returns health JSON — counts, data source, vocabulary and prompt size, model allowlist, which keys are set. Never a key. |

### The prompt is the map's vocabulary, not the map

Place data reaches the model through `search_places`, `get_place_details` and `find_nearby`, so the prompt
carries no rows — only the vocabularies `buildCatalog` counts out of the sheet: every `Type`, and every
sub-category heading a `description` ("Mexican restaurant"). Without the real words a model asked for *latino
restaurants* searched that phrasing and called a map holding 40 Latin American places empty. `search_places`
**OR**s `query` across name, type, sub-category and notes and resolves `type` against that vocabulary, so
*coffee shops* reaches `Cafe` while a word outside it (*barbecue*) narrows as a keyword instead of emptying the
result. Recounted per refresh: a new `Type` lands within the 5-minute cache window, no code change.

`get_place_details` takes a `fields` argument, so "what's the rating for Aba" returns that field, not a card to
pick through. **Names match in tiers** — exact, prefix, substring, all-words-present — and `matchPlacesByName`
returns only the best tier that hit, so a place whose notes mention "Kasama" cannot drown out Kasama itself;
*the museum* matches a dozen rows, so the tool returns candidates rather than guessing. `THEMES` maps a region
term (`caribbean`, `latin`, `asian`, `middle eastern`, `african`, `mediterranean`, `european`, aliases like
*west indian*) to every country, demonym and dish under it — left alone, a model reads *Caribbean food*
literally and finds two places where the map holds twenty.

### Everything is sized against an 8K context window

Allowlisted models get an **8,000-token context**, and prompt, schema, history and every tool result are
re-sent each round of the tool loop, so a three-round question has to fit four copies of the overhead. It lands
near **2.9K**, and stays there because:

- **List results carry only what a list answer says out loud** — name, type, sub-category, neighborhood,
  rating, address (`list: true` in `PLACE_FIELDS`); the rest needs `get_place_details`. Carrying every field
  per row costs 3× as much — a 12-place answer alone would rival the whole prompt.
- **Sub-category counts print only where they inform** (`count > 1`): 250 repeats of `" (1)"` spent 2.8K
  characters saying nothing. The list is capped at `MAX_VOCAB_CHARS` and the dropped tail is *announced*
  (`+N rarer ones not listed`) — a model told the list is complete stops searching.
- **The schema is terse and the prompt is verbose**, since the schema is re-sent every round and the prompt
  once. Caps: history 4×280 chars, results 12 places. `GET /` reports live prompt size, so drift shows up
  without a deploy.

### Streaming

No upstream round is streamed: a tool call can only be parsed from a whole JSON body, and the round where the
model stops calling tools is the round where it writes the reply. The Worker keeps that text and re-frames it
as the SSE the page already reads (`{"delta"}` frames, optional `{"error"}`, then `[DONE]`), chunked on
whitespace so a long answer paints in reading order. Re-asking with `stream: true` would cost a second
full-prompt call and can return nothing — a fresh sample of an answered turn sometimes calls a tool. Upstream
401/429/5xx map to sentences a visitor can act on; the client warns at 9s, gives up at 90s. Twelve silent
seconds under a `Retry-After: 12` read as a hung widget, so the first rate-limit wait opens the stream early
with a `{"notice"}` frame — status line only, never folded into reply or history, since once a byte is out
the real status code is spent.

### "Near me"

The one thing a prompt cannot answer alone. `NEAR_ME_RE` in `chicagoChat.js` — the only hardcoded language rule
left — decides whether to ask the browser for coordinates. The prompt then carries one line naming the
visitor's neighborhood (`nearestHood`, averaged from the coordinates of the places filed under each one, so no
hand-entered centroid table can drift); `find_nearby` does the geometry on demand, so the model never estimates
a distance, and past `FAR_AWAY_MI` (25) its result says the visitor is out of town rather than present a
700-mile drive as "nearby". Coordinates are rounded to 4 decimals (~11 m) before leaving the browser, sent
only on nearby questions, kept in memory 5 minutes, never stored.

### Running locally

Serve over HTTP rather than opening the file: `file://` has no origin for the sheet's CORS check, and
geolocation needs a secure context, which `localhost` counts as. First block is the map; the chat needs the
Worker too.

```sh
cd <repo root>
python3 -m http.server 8000     # then open http://localhost:8000/chicagoMap.html

cd assets/chicago_list/worker
cp .dev.vars.example .dev.vars          # gitignored; paste your API keys here
npx wrangler dev --config wrangler.toml # serves the Worker at http://127.0.0.1:8787
```

**The `--config` flag is not optional:** without it wrangler walks up, finds the repo-root `wrangler.jsonc`,
and dies trying to serve the repo's `.git` pack as static assets (`Asset too large … 112 MiB`). Use `wrangler
dev` here, not `deploy.sh` — that deploys to production. `chicagoChat.js` switches to the dev URL itself on
`localhost`/`127.0.0.1`. Port 8000 matters: it and 5500 (VS Code Live Server) are in `ALLOWED_ORIGINS`; any
other port gets `403` until added. Skipping the Worker leaves the map working and the chat saying it is not
connected.

### Deploying

**Prerequisites:** a free [Cloudflare account](https://dash.cloudflare.com/sign-up), a
[Gemini](https://aistudio.google.com/apikey) and/or [Groq](https://console.groq.com/keys) key, and
`WRANGLER_WORKER_NAME` plus at least one of `GEMINI_API_KEY` / `GROQ_API_KEY` in the repo-root `.env` (see
`.env.example`). With one key set, the other provider's models return a clear error.

```sh
bash assets/chicago_list/worker/deploy.sh
curl https://chicago-chat.chicagochat.workers.dev   # verify, after it prints the live URL
```

`deploy.sh` loads `.env`, pipes whichever keys are set in as Worker secrets — never touching shell history or
the repo — then `cd`s into `worker/` and deploys. That `cd` is what avoids the `Asset too large` failure above,
and the reason not to run wrangler from the repo root. It exits on any failure (`set -euo pipefail`), and
re-running it rotates a key, since secrets go up before the deploy. After the first deploy, put the printed URL
in `WORKER_URL` at the top of `chicagoChat.js` and commit it with `worker/` — nothing there holds a key. In the
health JSON, `"ok":true`, `"source":"sheet"` and `true` per provider under `"keyConfigured"` is the good state;
`false` means that secret push did not land, `"source":"snapshot"` that the sheet fetch failed.

## Data flow

```
Google Sheet ──gviz CSV──> chicagoData.js ────> chicagoMap.js   (markers, Type filter chips)
 (source of truth)     │    (per page load) │
                       │                    └── sheet unreachable? ──> chicago_layers.geojson
                       │
                       └──gviz CSV──> worker/worker.js ──> Gemini or Groq ──> chicagoChat.js
                                       (prompt, 5-min cache)  (page's choice)  (streamed reply)
```

Two independent readers of one sheet, both via Google's gviz CSV endpoint (`/gviz/tq?tqx=out:csv&gid=…`), which
needs no API key and echoes the requesting origin in `Access-Control-Allow-Origin`, so a static page can call
it. **The sheet must stay shared as "anyone with the link can view"** — otherwise the endpoint stops answering
and both readers fall back to the snapshot. Both merge rows by name + address, landing near ~550 places; the
exact count drifts with the sheet, which is why nothing hardcodes it. Coordinates resolve per row: the sheet's
`Lat`/`Lon` (filled by `geocodeSheet.gs`, preferred — no lookup), else `geocode_cache.json` keyed by address,
else neither — a `null` geometry, so no marker and no distance in a "near me" answer, though the row stays
searchable and counted.

## Output format

`chicago_layers.geojson` is a flat `FeatureCollection` of `Point` features, one per sheet row — no layer
grouping. Each property mirrors a sheet column and appears only when that cell was filled; popup and chat
degrade gracefully without any of them.

```json
{ "type": "FeatureCollection", "features": [
  { "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [-87.6678223, 41.9732297] },
    "properties": { "name": "Meeting House", "type": "Bar", "neighborhood": "Andersonville",
                    "address": "5025 N Clark St, Chicago, IL 60640", "description": "Gay bar",
                    "reviews": "shuffleboard, billards, arcade games, popcorn",
                    "phone": "(773) 696-4211", "website": "https://www.meetinghousetavern.com/",
                    "ratingsAverage": "4.6", "ratingsTotal": "272" } }
] }
```

## Updating

**Editing text, types, or neighborhoods:** edit the sheet — live on the next page load.

**Adding a place:** add the row, then give it coordinates via `Sheet -> Chicago Map -> Geocode missing rows`.
Until that runs the row is searchable but unmapped. Rows with `Lat`/`Lon` are never re-geocoded, so the menu
item is cheap to re-run. The chat picks the row up within 5 min, the map on next load.

**Refreshing the offline fallback**, worth doing occasionally so the snapshot does not drift:

```sh
python3 assets/chicago_list/geocode.py           # snapshot + geocode anything still missing
python3 assets/chicago_list/geocode.py --no-api  # snapshot only, no Nominatim calls
```

It fetches the sheet as CSV, loads `geocode_cache.json`, geocodes any row with neither sheet coordinates nor a
cache hit via [Nominatim](https://nominatim.openstreetmap.org) (1 req/sec per their usage policy, flushed every
25), then emits `chicago_layers.geojson`. `geocodeSheet.gs` is the normal path, since it writes coordinates
back into the sheet where the site reads them; `geocode.py` is for the snapshot only.
